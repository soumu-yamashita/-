# 社内チーム向けタスク管理アプリ 要件定義書

- バージョン：1.0（初版）
- 作成日：2026年11月16日
- 対象：初期リリース（MVP）
- 状態：実装に向けた要件案

## 1. 目的とコンセプト

「誰が・何を・いつまでに行うか」を共有し、期限漏れを防ぐ社内チーム向けタスク管理アプリを提供する。

担当者・期限・完了状態を一覧で把握できるようにし、担当の曖昧さ、対応漏れ、進捗確認の手間を減らす。

## 2. 想定ユーザーと利用範囲

| ユーザー | 主な利用目的 |
|---|---|
| 社内チームメンバー | タスクの登録、自分や他メンバーの担当・期限の確認、更新、完了報告 |
| チームリーダー | 未完了・期限超過タスクや担当の偏りの確認 |

初期リリースは、単一の社内チームを対象とする。招待された有効なメンバーは、チーム内の全タスクを閲覧・登録・編集し、完了状態を変更できる。リーダー専用のアプリ権限は設けない。

利用者の招待・無効化は運用管理者が行う。利用者管理画面は初期リリースに含めず、Supabaseの管理機能または管理者用の安全な運用手順で対応する。

## 3. 前提条件

- PCのWebブラウザーでの利用を主な対象とし、スマートフォンでも基本操作ができるレイアウトにする。
- 表示言語は日本語、日時の表示基準は日本時間（Asia/Tokyo）とする。
- 社内データをSupabaseとVercelに保存・処理することが社内規定で許可されていることを、実運用前に確認する。
- 初期認証方式は、招待メールによる初回パスワード設定後のメールアドレス・パスワード認証とする。
- 公開の新規登録は提供しない。社内SSO・多要素認証が必須の場合は、実運用前に認証要件を見直す。
- タスクには機密性の高い個人情報や認証情報を登録しない運用とする。

## 4. 初期リリースの機能要件

| ID | 機能 | 要件 |
|---|---|---|
| F-01 | ログイン・ログアウト | 招待済みの有効なメンバーがログインでき、ログアウトできる。未認証時はタスクにアクセスできない |
| F-02 | 初回設定・パスワード再設定 | 招待メールからパスワードを設定できる。ログイン画面から再設定メールを要求できる |
| F-03 | タスク登録 | タイトル、担当者、期限を必須として登録できる。詳細説明は任意。初期状態は未完了とする |
| F-04 | タスク一覧 | タイトル、担当者、期限、完了状態を表示する。初期表示は未完了タスク、期限の近い順とする |
| F-05 | タスク詳細 | 一覧から詳細を開き、詳細説明を含む登録内容を確認できる |
| F-06 | タスク編集 | 全メンバーがタイトル、詳細説明、担当者、期限を変更できる。完了済みタスクも編集できる |
| F-07 | 完了状態変更 | 未完了から完了、完了から未完了へ変更できる。完了時は完了日時を保存し、未完了に戻した際はクリアする |
| F-08 | 絞り込み | 担当者と状態（未完了・完了・すべて）で絞り込める。条件は組み合わせ可能とする |
| F-09 | 期限超過表示 | 未完了かつ期限が日本時間の当日より前のタスクに「期限超過」と表示する。色だけに依存しない |
| F-10 | 操作結果・エラー表示 | 保存成功、入力不備、通信失敗を表示する。保存失敗時は成功扱いにせず、入力内容を維持して再試行できる |

### 4.1 入力・業務ルール

- タイトル：前後の空白を除いて1〜100文字。空白のみは不可。
- 詳細説明：任意、最大5,000文字。プレーンテキストとして扱う。
- 担当者：有効な社内メンバーから1名を選択。未割り当てや複数担当は扱わない。
- 期限：有効な日付を必須とし、時刻は扱わない。過去の日付も登録可能とし、保存後は期限超過ルールを適用する。
- 期限当日のタスクは期限超過に含めず、完了済みタスクにも期限超過表示を付けない。
- 同一期限のタスクは作成日時の新しい順、さらにID順で安定して表示する。
- 二重送信を防ぐため、保存処理中は同じ操作を再送信できないようにする。
- 同時編集で既存の変更を上書きしないよう、更新時にデータの版を照合する。競合時は再読み込みを促し、入力内容を確認できるようにする。
- 無効化されたメンバーの既存タスクは保持する。担当者名を表示し、別の有効なメンバーへ再割り当てできる。無効な担当者を新たに選択することはできない。
- タスク削除は初期リリースに含めない。

## 5. 画面要件

| 画面 | 主な表示・操作 |
|---|---|
| ログイン | メールアドレス・パスワード入力、ログイン、パスワード再設定への導線 |
| パスワード設定・再設定 | 招待・再設定リンクの検証、パスワード登録、リンク無効時の案内 |
| タスク一覧 | 一覧、担当者・状態フィルター、新規登録、詳細への導線、完了切り替え、ログアウト |
| タスク登録 | タイトル、詳細説明、担当者、期限の入力、保存、キャンセル |
| タスク詳細・編集 | 登録内容の確認・編集、保存、完了切り替え、一覧へ戻る導線 |

一覧の初期表示は最大50件とし、続きのページに移動できる。該当タスクがない場合、読み込み中、取得失敗の場合を区別して表示する。ログイン後の最初の画面はタスク一覧とする。

## 6. データ要件

### 6.1 メンバー（profiles）

| 項目 | 型・制約 | 用途 |
|---|---|---|
| id | UUID、主キー、Supabase AuthのユーザーIDと対応 | メンバー識別 |
| display_name | 必須文字列 | 担当者名の表示 |
| is_active | 真偽値 | アプリ利用可否・新規担当者選択の制御 |
| created_at | タイムゾーン付き日時 | 作成日時 |

認証用メールアドレスとパスワードはSupabase Authで管理する。パスワードをアプリ独自のテーブルに保存しない。メンバー情報の作成・有効化・無効化は管理者のみが行う。

### 6.2 タスク（tasks）

| 項目 | 型・制約 | 用途 |
|---|---|---|
| id | UUID、主キー | タスク識別 |
| title | 必須文字列、最大100文字 | タイトル |
| description | 任意文字列、最大5,000文字 | 詳細説明 |
| assignee_id | 必須UUID、profilesを参照 | 担当者 |
| due_date | 必須DATE | 期限 |
| status | todo / done | 未完了・完了 |
| completed_at | 任意のタイムゾーン付き日時 | 完了日時 |
| created_by | 必須UUID、profilesを参照 | 作成者 |
| created_at | タイムゾーン付き日時 | 作成日時 |
| updated_at | タイムゾーン付き日時 | 最終更新日時 |
| version | 必須整数、更新時に加算 | 同時編集の競合検出 |

期限は日付として保存し、各操作の日時はUTCで保存して日本時間で表示する。完了状態と完了日時の整合性をサーバー側でも保証する。初期リリースではタスク変更履歴の専用テーブルは設けない。

## 7. 技術構成

| 領域 | 採用技術 |
|---|---|
| 画面・サーバー処理 | Next.js（App Router） |
| 言語 | TypeScript |
| UI | Tailwind CSS、shadcn/ui |
| データベース | Supabase PostgreSQL |
| 認証 | Supabase Auth |
| ホスティング | Vercel |
| E2Eテスト | Playwright |

ブラウザーからNext.jsの画面・サーバー処理を利用し、Supabase Authで認証、PostgreSQLでデータを管理する。初期リリースでは別のバックエンドサーバーを設けない。

更新処理はNext.jsのサーバー側で認証・入力検証を実施し、利用者のセッションに紐づけてデータベースを操作する。データベース定義とRLSポリシーはマイグレーションで管理する。ライブラリの具体的なバージョンは実装開始時に互換性のある安定版を選び、ロックファイルで固定する。

## 8. セキュリティ・アクセス制御

- 全タスクとメンバーデータにRLSを設定する。
- 未認証ユーザーと無効化されたメンバーはデータを読み書きできない。画面遷移制御だけでなくデータベース側でも拒否する。
- 有効なメンバーは全タスクの参照・登録・編集が可能。通常ユーザーによるタスク削除、メンバー情報の更新は許可しない。
- 作成者・作成日時はクライアントの任意入力を信用せず、作成後の変更を許可しない。
- 管理者用キーはブラウザーへ渡さず、通常のタスク操作にも使用しない。
- 秘密情報は環境設定で管理し、リポジトリやログに保存しない。
- 通信はHTTPSを利用する。
- 認証エラーや再設定要求の表示で、アカウントの存在を不用意に明らかにしない。
- Supabaseの招待・再設定リンクのリダイレクト先は承認したアプリURLに限定する。
- 開発・テスト環境と本番環境のデータおよび認証設定を分離する。

## 9. 非機能要件

| 項目 | 初期リリースの要件 |
|---|---|
| 想定規模 | メンバー50名、同時利用10名、タスク10,000件を設計上の目安とする |
| 応答性能 | 通常の社内回線で、一覧の最初の50件の表示と保存操作の完了表示を原則3秒以内にすることを目標とする。初期リリース前に検証環境で計測する |
| 対応ブラウザー | リリース時点のChrome・Edge・Safariの最新安定版 |
| 操作性 | キーボードで主要操作ができ、入力欄にラベルを付ける。状態・エラーは文字でも伝える |
| 障害時の挙動 | エラーを表示し、保存の成否が不明な場合は再取得して確認できる。未保存の内容を不用意に消さない |
| 運用監視 | アプリのサーバーエラーを確認できる状態にする。ログにパスワードやタスク本文を出力しない |
| バックアップ | 本番運用前にSupabaseの選択プランでバックアップ・復元機能を確認し、復元手順を記録する。必要な保存期間と復旧目標は運用責任者と決める |

規模・性能は現時点の設計上の仮定であり、稼働保証値ではない。公開前の計測結果に応じて調整する。

## 10. 受け入れ条件

| ID | 確認内容 | 合格条件 |
|---|---|---|
| A-01 | アクセス制御 | 未ログイン・未招待・無効化済みの利用者が、画面・直接のデータ操作の両方でタスクを取得・変更できない |
| A-02 | 初回認証 | 招待メールからパスワードを設定してログインでき、ログアウト後はデータへアクセスできない |
| A-03 | 登録 | 必須項目を入力して登録すると一覧に反映され、再読み込み後も内容が保持される |
| A-04 | 入力検証 | 空タイトル、担当者未選択、不正な日付、文字数超過は拒否され、修正箇所を確認できる |
| A-05 | 編集 | タイトル・詳細説明・担当者・期限の変更が保存され、別のメンバーの画面でも再取得後に確認できる |
| A-06 | 完了管理 | 完了にすると未完了一覧から外れ、完了フィルターで確認できる。未完了へ戻すと再表示される |
| A-07 | 期限判定 | 日本時間で昨日が期限の未完了タスクだけが期限超過となる。当日期限や完了済みタスクは期限超過にならない |
| A-08 | 一覧・絞り込み | 担当者と状態の条件を組み合わせて絞り込める。51件以上でもページ移動で対象タスクを確認できる |
| A-09 | 通信失敗 | 保存失敗時にエラーが表示され、入力が残り、復旧後に再試行できる |
| A-10 | 同時編集 | 同じ版を開いた2人が更新した場合、後の更新で競合を検出し、先の変更を黙って上書きしない |
| A-11 | メンバー無効化 | 無効化後は既存セッションでもデータ操作を拒否する。既存の担当タスクは保持され、他メンバーへ再割り当てできる |
| A-12 | パスワード再設定 | 再設定メールから変更したパスワードでログインできる。無効・期限切れリンクには案内を表示する |

Playwrightで登録→一覧確認→編集→完了→未完了への復帰を確認する。RLS・無効化・入力制約・競合検出は、画面テストに加えて直接のデータ操作を含む結合テストで検証する。ビルドと型チェックを実行し、公開前には実際の認証メールの配信とリンク遷移も確認する。

## 11. 初期リリースに含めない機能

- タスクの削除・アーカイブ
- タスク期限のメール・チャット通知（招待・パスワード再設定メールは対象に含む）
- コメント、ファイル添付、変更履歴表示
- カレンダー、カンバン、リアルタイム同期
- 繰り返しタスク、サブタスク、複数担当者
- 優先度、ラベル、全文検索
- 複数チーム・複数プロジェクト、詳細な役割・権限設定
- 集計レポート、外部サービス連携、AI機能
- メンバー招待・管理用のアプリ画面

## 12. 実運用前に確定・準備する事項

以下はローカル開発の開始を妨げないが、実運用前に確定する。

- 社内のクラウド利用・データ保管・認証規定への適合。
- 本番のVercel・Supabaseプロジェクト、配置リージョン、公開URL、運用管理者。
- 招待対象メンバー、招待・無効化・担当変更の運用手順。
- 認証メールの送信元と本番向けSMTP設定、送信制限、配信テスト。
- サービス料金、バックアップ保存期間、復旧目標、障害時の連絡先。
- 想定人数・データ量と性能計測結果の確認。

本書は要件の整理であり、アプリの実装・デプロイ・環境の稼働検証が完了したことを示すものではない。
